Did RL on Git Tool Use Transfer? We Finally Checked

We trained a 2B model with RL on git tool use and tested it on tasks it never saw. It got better on unseen tasks of the kind it trained on, and no better on harder ones. What it learned was mostly a way of answering that our grader likes.

Update, November 18, 2026. After publishing, we tested the trained model on a different tool server. It did worse than the untrained model. See the update below; two sentences that said this was untested have been changed.

The question we left open

The March post ended with a question: after RL training on git tasks, does the model generalize, or did it memorize the task templates? Until now nothing in this project could answer it. The model was trained and scored on the same episodes, and the number we reported was the training reward, which includes a bonus for calling tools.

This post reports one run built to answer it.

What we changed to make it answerable

  • A held-out set. The 200 L1–L4 episodes are split by task family: 147 for training, 53 held out. Paraphrases of one task always land on the same side.
  • Harder tasks the model never trains on. 96 “L5” tasks in 24 patterns: 64 use the 13 training tools on multi-step problems (commit one file but not another, branch from a specific commit), and 32 need tools that are not in training at all (stash, cherry-pick, merge).
  • Success instead of reward. A rollout counts only if its outcome is exactly right. For read tasks we report two gradings: literal looks for git's own output text in the final answer, facts looks for the same facts in any wording.
  • A smaller model. The untrained Qwen3.5-4B already solves most of these tasks (about 0.9 on held-out by facts and on L5, in a local test with a quantized copy), which leaves little room to measure a gain. We used Qwen3.5-2B, which leaves room on both the held-out set and L5.

The base model is measured inside the training run, before the first step, through the same pipeline as the trained model.

What the base model already did

Untrained Qwen3.5-2B, three attempts per task:

The model starts well above “broken”. It already knows which git tool to call and already completes most write tasks. Most of the gap on read tasks is between the two gradings: the model often gives a correct answer in its own words and misses the exact string.

It did not memorize. The held-out episodes improved as much as the training episodes. We checked the run's records: no held-out or L5 task shares an id, a prompt or a family with anything the model trained on. Held-out here means an unseen task in a familiar setting: the same repository templates, the same tools and the same grader.

It did not get better at harder git tasks. L5 with the training tools did not move. L5 with new tools went down, though the interval reaches zero.

What the model actually learned

The held-out number looks like a success. The transcripts say otherwise.

Base modelAfter 25 steps
Final answer, median length264 characters2,244 characters
Tool calls per task3.04.7
Turns with more than one tool call8%44%
Answers cut off (token or turn limit)3%31%

(Held-out set.) The trained model calls several tools at once and then writes a long answer that repeats what the tools returned. Our read grader only checks that the expected strings or facts appear somewhere in the final answer, so a long answer passes. It also passes when it says wrong things. Asked whether a clean repository has uncommitted changes, one trained answer said no, then added “All files have been staged for the next commit” and “Your changes are ready to be committed”. Both gradings gave it full marks.

That explains the table. The gain is on read tasks (+0.58 literal on held-out reads), where length is rewarded. Write tasks are graded on the repository's final state, which length cannot satisfy; they went from 0.88 to 0.97. And the habit carries to any read task with this grader, seen or unseen, which is why held-out matches training.

On L5 the same habit hurts. The five patterns that end in a commit fell from 0.37 to 0.12. In the failed attempts we read, the model's first move is to call git_status, git_log and git_add . together, before it has seen which files exist. That stages the file the task said to leave alone. We picked this group of patterns after looking at the per-pattern numbers, so treat it as a description, not a tested result.

We had seen the same thing in July without recognizing what it meant: in two 50-step runs on Qwen3.5-4B, all of the measured gain was in read episodes whose grader wanted git's literal output, and the model copied more tool output over training.

Update: we tested a different tool server

Added November 18, 2026, about two hours after publishing.

After publishing, we evaluated the last saved model of the run (step 44) on tasks with tools it never trained on: four filesystem tools, no git. The tasks are graded on the files left behind or on one exact answer line, so a long answer cannot pass them.

SetBase modelAfter trainingChange
Filesystem, harder tasks0.5450.410−0.135 [−0.240, −0.028]
Filesystem, basic tasks0.7850.688−0.097 [−0.167, −0.028]

The trained model did worse than the untrained one on both sets. The habits it picked up on git came with it: its answers were four to five times longer, it made more tool calls, and more of those calls failed.

We chose the comparison on the harder set as the main result before running it. Both sets were sized using the untrained model only.

On the git sets, step 44 looks like step 25: held-out success 0.97, L5 with the training tools 0.48 (base model 0.48), L5 with new tools 0.63 (base model 0.67).

This is still one run of one small model.

So, does it transfer?

  • To unseen tasks of the same kind: yes, but what transfers is an answering style that fits the grader.
  • To harder tasks with the same tools: no.
  • To new tools: no.
  • To a different tool server: no, it got worse. See the update.

The reward did what it was written to do. “The final answer contains the expected strings” is cheapest to satisfy by writing more, and 25 steps of RL found that.

What this run cannot tell you

  • One run, one seed, 25 steps. The run was planned for 50 steps. It was paused at step 44 on cost. The main tables are from step 25; the update evaluates the step-44 model.
  • One small model. Nothing here is about Qwen3-4B-Instruct-2507, the model in the March post. That model is no longer available on the platform, and its runs were never evaluated on held-out tasks.
  • Full fine-tuning at a low learning rate (1e-6), the platform's only mode now. The earlier runs used LoRA at 1e-5.
  • The grader cannot separate a correct concise answer from a long one, so we cannot say how much of the read gain, if any, is better git use.

What it cost, and why

The run cost $48.51 against an estimate of $17 to $21. We skip groups of rollouts that all earn the same reward, because they carry no learning signal. At the start that kept about 55% of groups. As the model converged on its new habit, rollouts within a group became identical: 23% were kept at step 25 and 5% from step 40. A training step went from under a minute to about 25 minutes, almost all of it spent generating rollouts that were thrown away.

This is the failure the effective-batch post describes, seen from the billing side. Success on the training rollouts of the last steps was 0.99.

What we would do differently

  • Grade read answers for what they get wrong, not only for what they contain, or cap the answer length.
  • Evaluate on held-out and harder tasks from the first run, and report success, not the training reward.
  • Measure the base model before claiming a gain.
  • Stop a run when the share of kept groups falls below a set level, instead of paying for it to finish.
