November 25, 2026 Reinforcement Learning Tool Use Evaluation Diagnostics

From 25.0% to 46.9% on Unseen Olympiad Math for $0.00 on Free Inkling-2-Mini

Tinker made Inkling-2-Mini free to train and sample. I put it through thinking-effort tuning, diagnostic-driven text RL, and multi-turn Python tool-integrated reasoning (TIR) RL at $0.00 spend, and open-sourced tinker-inspect along the way.

Following up on last week's transfer failure

In last week's post, RL on git tool use failed to transfer to harder tasks for two concrete reasons: a loose read grader rewarded longer answers instead of better tool use (median length jumped from 264 to 2,244 characters), and constant-reward group dropping quietly drove the run bill to $48.51.

On November 25, Tinker made thinkingmachines/Inkling-2-Mini:peft:65536:free free to train and sample for accounts with a positive balance ($0.00 across prefill, cached prefill, sampling, and training). That gave me a clean way to test the exact opposite setup at zero compute cost:

  • An ungameable exact-match verifier. Competition math problems from Polaris-Dataset-53K filtered to exact rational answers, graded strictly on the reduced fraction inside the last \boxed{}. Longer answers cannot fool the grader.
  • Strict train/test separation. Every evaluation set is deduplicated against training by ID, normalized text, and alphanumeric-stripped text. In particular, zero 1/8 Olympiad problems ever appear in training.
  • Pre-filter diagnostics on every run. Before trusting a training curve or launching a second run, I inspected pre-filter rollout summaries, KL0 alignment, truncation rates, stragglers, and paired bootstrap confidence intervals using a tool I built and open-sourced during this sprint: tinker-inspect.

1. Tuning thinking effort mattered more than doubling max_tokens

Before touching math RL, I evaluated untrained Inkling-2-Mini:peft:65536:free on our existing multi-turn git tool benchmark, including the 32 unseen-tool L5 tasks (l5_new_tools, 3 attempts per task = 96 rollouts per condition). On the default tml_v0 renderer, Inkling-2-Mini scored 87.5% — behind Qwen3.5-4B's 90.6% — with 32 max_turns hits and 11 mid-thinking truncations.

Inspecting the paired transcripts showed why: TmlV0Renderer hardcodes DEFAULT_EFFORT = 0.9. On multi-turn tool calls, high effort caused the model to over-deliberate inside <|content_thinking|>, clip at max_tokens=1024, and burn turns retrying reads instead of invoking the unseen write tools.

Doubling max_tokens from 1024 to 2048 at effort=0.9 barely helped. Lowering the effort parameter to 0.2–0.5 solved the problem completely:

Why did less thinking effort beat more? The effort=0.9 @ 2048 control isolates the mechanism. Doubling the token budget cut mid-thinking truncations from 11 to 5, yet max_turns failures actually climbed from 32 to 36 and accuracy barely moved (87.5% → 89.6%). Reading the failed transcripts showed hesitation loops rather than budget starvation: because the synthetic git fixtures have quirky placeholder file contents (for example, Dockerfile lines inside main.py), high effort caused the model to second-guess the task (“this commit looks suspicious”) and burn all 10 turns on repeated git_log / git_show / git_diff reads without ever calling git_merge or git_cherry_pick. At effort=0.2–0.5, it checked the repo once, executed the requested write tool, and finished in ~6 turns with 1–2 max_turns hits.

Lowering effort from 0.9 to 0.2–0.5 lifted unseen-tool success from 87.5% to 94.8%–95.8% at 2.7×–3.9× fewer action tokens and zero thinking truncations. One quirk worth noting: effort=0.0 still generates thinking tokens and actually used more tokens than effort=0.2. I pinned all RL experiments below to effort=0.2. You can inspect the paired Qwen vs. Inkling transcripts directly in the interactive diff report.

2. Diagnostic-driven RL turned a flat run into +10.9 pp

Next I ran 16 steps of stable_reinforce RL on Polaris competition math problems (LoRA rank 32, effort=0.2). Run #1 (max_tokens=2048, group_size=4, lr=4e-5, difficulties 2/8..4/8) came back completely flat on held-out Polaris 2/8..4/8 (64 tasks × 2 attempts): 0.289 → 0.289 (+0.0 pp).

In standard metrics.jsonl logs, nothing looked obviously broken: KL0 was exact (0.000000), and env/all/by_group/frac_mixed read 1.0 because tinker-cookbook computes metrics after dropping constant-reward groups. Reconciling pre-filter train_rollout_summaries.jsonl in tinker-inspect immediately showed why Run #1 stalled:

  • 61.3% of turns hit max_tokens=2048 and were cut off mid-thought before emitting \boxed{}.
  • 73% of sampled groups were discarded as constant-reward (109 of 192 groups were all-bad).

Acting directly on those two alerts in Run #2 — doubling max_tokens to 4096, raising group_size from 4 to 8, raising lr to 1.5e-4, and training on 3/8..6/8 — cut truncation from 61.3% to 19.8%, dropped all-bad groups from 109 to 25, tripled trained tokens (384k → 1.14M), and turned the flat run into a statistically significant held-out gain:

  • Held-out Polaris 2/8..4/8 (64 × 2, 4096 tok): 56.2% → 67.2% (+10.9 pp, 95% CI [+2.3, +20.3], 15 wins / 3 regressions / 46 ties), while output tokens dropped 5.7% (2,539 → 2,395) and eval wall time fell 20% (497s → 397s).
  • Held-out MATH-500 Level 5 (64 × 2, 2048 tok): held steady at 81.2% → 81.2% with 11.5% fewer thinking characters (no degradation on easier math).
  • Run #3 (Steps 16 → 32 continuation, lr=8e-5, 2/8..5/8): zero-shot transfer to strictly harder OOD Polaris 1/8 Olympiad problems (48 × 2, zero 1/8 problems in training) climbed monotonically from 25.0% (Base) → 34.4% (Step 16) → 37.5% (Step 32) (+12.5 pp, 95% CI [+2.1, +22.9], 13W/3R/32T) while compressing output tokens 9.8% (2,855 → 2,574).

Side-by-side training diagnostics for Run #1 vs. Run #2 are hosted in the comparison report, and Run #2's full report is here.

3. Multi-turn Python TIR RL: +21.9 pp on OOD Olympiad math

Text-only RL topped out at 37.5% on OOD Polaris 1/8 Olympiad problems. Next I switched to Tool-Integrated Reasoning (TIR) — interleaving chain-of-thought reasoning with executable tool calls (here, running Python scripts to test small cases, check algebra, or compute exact fractions) before giving a final answer. I gave Inkling-2-Mini:peft:65536:free a native tml_v0 run_python tool running Python 3 in an isolated local subprocess with a 3-second process-group timeout and up to 4 turns per episode (max_tokens=3072 per turn, effort=0.2), then ran 16 steps of multi-turn TIR RL on Polaris 2/8..5/8 (again with strictly 0 overlap against 1/8 or held-out 2/8..4/8).

Because TmlV0Renderer has the sequence extension property, multi-turn tool trajectories reuse KV prefixes cleanly: tinker-inspect reported 55% prefix-cacheable prefill across 2.43M prefill tokens, only 5.2% max-token truncation, exact KL0 (0.000000) on every step, and $0.00 total spend across 30.2 minutes of wall time.

Here is the complete 5-rung ladder on the exact same 48 unseen OOD Polaris 1/8 Olympiad problems (2 attempts each = 96 rollouts per condition):

Every dimension moved in the right direction at once. Relative to Base TIR (31.2%), 16 steps of multi-turn RL added +15.6 pp (95% CI [+6.2, +26.0], 15 wins / 3 regressions / 30 ties), lifted format_ok from 58.3% to 80.2% (+21.9 pp), cut Python tool errors by 36% (0.344 → 0.219, CI [−0.240, −0.021]), cut mean output tokens by 34% (2,698 → 1,781, shorter on 45 of 48 tasks), and ran 1.84× faster (421s → 230s). Unlike last week's git run, RL learned to think less and execute cleaner, tighter Python checks instead of padding outputs.

4. Open-sourcing tinker-inspect v0.2

Every diagnostic that guided these runs is now packaged in tinker-inspect — a zero-dependency CLI (Python 3.11+ stdlib only) that generates single-file, zero-CDN HTML reports from any Tinker RL log_path directory:

# Run directly with uvx (no install needed)
uvx --from git+https://github.com/BrunoSE/tinker-inspect tinker-inspect /path/to/tinker/log_dir

# Compare 3+ checkpoints or methods as a paired progression curve + Pareto + task heatmap
tinker-inspect series \
  "Base CoT=base.jsonl" "Step 16=step16.jsonl" "TIR RL=tir.jsonl" \
  --sanitize-paths --out series.html

# Live-monitor an active Tinker RL run and exit 2 on KL0 drift or health failure
tinker-inspect watch /path/to/active/log_dir --interval 5 --fail-fast
  • inspect — checks sampler-trainer KL0 across every step, reconciles pre-filter train_rollout_summaries.jsonl to surface hidden constant-reward drop rates, reconstructs multi-turn prefill amplification and prefix-cache hit rates, plots per-step straggler Gantt charts from timing_spans.jsonl, and flags max-token truncation, verbosity drift, and tool execution errors.
  • diff & series — compares two or more evaluation JSONLs (verifiers v1, legacy vf-eval, git_tool_rl, or native rollout JSONLs, with prompt-fallback pairing when task IDs differ) with deterministic 95% bootstrap CIs, accuracy-vs-tokens Pareto charts, per-task trajectory heatmaps, and expandable side-by-side transcripts.
  • compare — overlays two Tinker RL runs side-by-side to verify whether a diagnostic fix actually improved truncation, drop rate, and throughput.
  • watch — tails an active Tinker RL run in the terminal with deduplicated alerts and optional --fail-fast.

Browse all six live interactive demos at brunose.github.io/tinker-inspect.

5. Two small upstream PRs to tinker-cookbook

Running into real friction while building these experiments also produced two small upstream pull requests to thinking-machines-lab/tinker-cookbook:

  • PR #1026 (merged): added eval defaults for thinkingmachines/Inkling-2-Mini:peft:65536:free so BenchmarkConfig.for_model() no longer raises Unknown model.
  • PR #1027 (open, 7/7 CI green): exposed default_effort on TmlV0Renderer and added named presets (tml_v0_low_reasoning, tml_v0_medium_reasoning, tml_v0_high_reasoning, tml_v0_xhigh_reasoning) matching sample_reasoning.py so any RL, SFT, or benchmark pipeline can configure Inkling thinking effort via renderer_name.

What these runs cannot tell you

  • Rational-answer subset of Polaris. Training and evaluation filtered Polaris to problems whose gold answer parses as a finite rational number, so exact-match grading is clean and deterministic; symbolic or proof-style Olympiad answers are excluded.
  • Sample size and single seed per stage. OOD 1/8 uses 48 problems × 2 attempts (96 rollouts) and held-out 2/8..4/8 uses 64 × 2 (128 rollouts), with one RL training seed per 16-step stage. The main gains (+15.6 pp and +21.9 pp on OOD 1/8, +10.9 pp and +11.7 pp on 2/8..4/8) are well outside their 95% paired bootstrap intervals, while smaller differences like Step 16 vs. Step 32 on OOD 1/8 (46.9% vs. 42.7%) are noisy.
  • One model family. All RL runs here use thinkingmachines/Inkling-2-Mini:peft:65536:free at effort=0.2. Whether the same 16-step TIR jump holds at other effort settings or on non-Inkling models is untested here.
