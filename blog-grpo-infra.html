How Multi-Turn Git RL Rollouts Actually Run

Not Temporal. Not a custom trainer cluster you maintain by hand. Here is the concrete path from a natural-language goal to a GRPO update for git tool use on Prime Intellect + verifiers.

◆

Earlier posts argued that mean reward is a bad solo health metric for agentic GRPO, and that reward design can erase the learning signal. This post is the plumbing: what actually executes when you train a multi-turn git agent.

Stack, honestly:

  • Environment package: Python, verifiers, GitPython, temp-dir sandboxes
  • Trainer: Prime Intellect hosted GRPO (prime-rl under the hood)
  • Delivery: versioned env wheel on the Environments Hub, config TOML + CLI

No custom Temporal workflows and no hand-rolled gRPC reward service for these runs. The interesting complexity is still real: isolation, determinism, multi-turn tool loops, group scoring, and filters.

1. Ship the environment as a versioned package

The unit of deployment is not a git repo checkout on the GPU box. It is a built wheel pushed to the Hub:

cd environments/git-orchestration
prime env push --auto-bump
# e.g. bstefoni/git-orchestration@0.7.1 (live ablation runs; current package is v0.8.0)

Training configs pin that id. When you change reward logic, you bump the version and relaunch. Old runs keep the old package. That versioning is the main “CI for RL envs” property that matters in practice: you cannot accidentally mix A0 scoring from Monday with A3 code from Tuesday inside one confusing blob.

Ablations ride an env var into the worker:

prime rl run configs/lab/ablation_A0_short.toml \
  -e GIT_ORCH_ABLATION=A0

load_environment() reads GIT_ORCH_ABLATION, selects a RewardConfig, and closes over it in the group reward function. Same wheel, different scoring recipes.

2. One episode = one disposable git universe

Before the model acts, the env creates state:

  1. setup_state builds a temp directory git repo from a template (clean, dirty, staged, multi_branch) with a seed.
  2. It snapshots initial state (HEAD hash, branches, cleanliness, etc.).
  3. Dynamic answer fragments like $head_commit_hash are resolved against that snapshot so the model must report real values, not memorized strings.
  4. After the rollout, cleanup snapshots the final repo, then deletes the temp dir.

Isolation is boring and non-negotiable. Write episodes mutate repos. Without per-rollout sandboxes, one trajectory poisons the next. Seeds keep the same episode id reproducible across the 8 rollouts in a GRPO group so “same prompt, different samples” is a fair comparison.

3. Tools the model sees vs tools the env runs

There are 13 git tools (status, log, show, diffs, branch, add, commit, checkout, …). The model never receives repo_path. Registration looks like:

self.add_tool(tool_func, args_to_skip=["repo_path"])

On every call, update_tool_args injects the episode’s path. That is a small design choice with large security and schema benefits: the policy cannot invent paths; tool JSON schemas stay clean; reward and tools share one authoritative workspace.

Tool implementations are thin GitPython wrappers that return strings. Errors surface as tool messages. The multi-turn loop is “model emits tool call → env executes → tool result message → repeat” until a final assistant message with no tool calls, or max turns (10).

4. Anatomy of one training step

For the short comparison runs we used:

  • batch_size = 128 prompts
  • rollouts_per_example = 8 samples per prompt
  • Up to 10 tool turns per sample

Conceptual flow:

for step in 1..max_steps:
  sample up to 128 goals from the episode dataset
  for each goal:
    spawn 8 independent sandboxes (same template + seed)
    for each of 8 rollouts:
      multi-turn tool loop against that sandbox
      score reward in [0, 1]
    GRPO advantages within the group of 8
  apply filters (e.g. drop groups with zero advantage)
  optimizer update on what remains  # "effective batch"

That last line is where the earlier posts connect. You can spend a full step of GPU and still train on a tiny effective batch if filters discard most groups. Mean reward can still look excellent.

5. Scoring is a first-class service inside the env

Reward is not a separate microservice. It is a group-level function inside the env package, invoked after rollouts complete:

  • Read episodes: fraction of expected fragments in the final assistant text (A0), or also in tool text (A3 bug mode).
  • Write episodes: fraction of expected final-repo conditions (branch exists, clean tree, commit message substring, …).
  • Format gate: no tool calls → 0 (unless ablation turns the gate off).
  • Tool bonuses: small credit for successful tools; elevated write-tool bonus in A0.

We also log group metrics (mean/std by read vs write, variance-starved flags). Those lines are for debugging reward health; the trainer’s own filter metrics (zero-advantage rate, effective batch) are what killed A3 in production logs.

6. Why step 0 can take forever

Multi-turn rollouts dominate wall time. Each of 128×8 trajectories may issue several model calls and git operations. In practice the orchestrator sits on “batch filling” for a long time before the first step metrics appear. That is expected for this env class; it is not a stuck job unless logs show errors or filter empty-batch loops.

When A3 died, it was not sandbox thrash. It was consecutive steps where post-batch filters dropped every rollout (consecutive empty batches: 10/10), then BackoffLimitExceeded. The infrastructure did its job: it refused to pretend an empty training signal was a successful step forever.

7. What you operate day to day

The operator surface is intentionally small:

prime env push
prime rl run configs/lab/....toml -e GIT_ORCH_ABLATION=A0
prime rl logs <run-id>
prime rl metrics <run-id>
prime rl progress <run-id>

Locally, unit tests and an offline ablation harness score fixed policies without GPUs. That is how we measured “perfect vs empty final” advantages before spending cluster time. Hosted runs then checked whether those scoring differences show up as zero-advantage rate and effective batch under real GRPO.

8. Design principles that mattered

  1. Deterministic sandboxes per rollout — fair groups, no cross-talk.
  2. Hide privileged args — model never owns the filesystem path.
  3. Version the env, not tribal knowledge — wheel + Hub id beats “whatever is on the box.”
  4. Score in-process — fewer moving parts than a remote reward API for this scale.
  5. Log filters, not only reward — the health of GRPO is contrast and kept batch size.
  6. Offline policy scoring before live train — cheaper way to catch lying rewards.

What this is not

  • Not a full open-source dump of the trainer internals (those live in Prime’s stack).
  • Not a claim that you need Kubernetes YAML to reproduce the insight; you need a correct env contract and metrics that surface filtering.
  • Not Temporal/Kafka architecture cosplay. If we had built a custom multi-tenant trainer, that would be a different post.

Takeaway

The infrastructure for this project is a thin, ruthless loop: versioned env → parallel sandboxed multi-turn rollouts → group rewards → filters → GRPO update. Most of the research leverage sits in the env and the reward. Most of the operational leverage sits in watching what the filters leave behind.

If mean reward is the vanity metric, effective batch is the capacity metric. The pipeline above is how that capacity gets created and destroyed.
