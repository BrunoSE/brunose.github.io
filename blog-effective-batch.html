Effective Batch Is the Real KPI for GRPO Tool-Use Runs

Mean reward looked healthy on every ablation. Zero-advantage rate and effective batch size told you which run would die.

If you only watch mean reward during agentic GRPO, you will miss the failure mode that actually ends runs.

We trained the same multi-turn git tool-use environment three ways, changing only the reward recipe. Short hosted runs: Qwen3.5-4B, 50 steps, batch size 128 prompts, 8 rollouts per prompt, env bstefoni/git-orchestration@0.7.1. Mean reward was high for all three. Only one finished in good health. One finished weak. One starved to death.

Setup in plain terms

Each training step roughly looks like this:

  1. Sample many prompts (goals like “report the HEAD commit hash”).
  2. For each prompt, sample a group of 8 rollouts (same goal, different samples).
  3. Score every rollout with the reward function (0 to 1).
  4. GRPO computes advantages inside each group: better-than-group-mean rollouts get positive updates, worse ones negative.
  5. The trainer may filter out groups that give no learning signal (for example every rollout ties), so the update uses only what is left.

So “batch 128” is not 128 independent gradients. It is up to 128 prompts × 8 rollouts, then filters. If filters throw almost everything away, the effective batch is tiny even though you paid for a full rollout step.

What A0 / A1 / A3 actually change

Same tools, same episodes, same model. Only scoring differs:

  • A0 (baseline): on read tasks, only the model’s final message is checked for correct values. Write tools get a slightly higher bonus than read-only tools when the write outcome is not yet correct (0.2 vs 0.1). That bonus is a “you’re trying the right class of action” signal.
  • A1: same final-message rule, but write tools no longer get the elevated bonus (everything tool-related scales like 0.1). Offline, that erased the preference for write attempts when outcomes were still zero.
  • A3: on read tasks, correct strings found in tool outputs also count (the original bug). Calling git_status and saying “Done” can score almost as well as reporting the real answer.

Zero-advantage rate (platform filter): share of groups the trainer treats as having no usable within-group contrast. In practice this is almost always “everyone scored the same,” so GRPO advantages are ~0. High means most of your rollouts never enter a useful update.

Effective batch size (platform metric, reported as a fraction of the nominal batch): after filters, how much of the step still contributes to training. On these runs the nominal batch is 128 prompts. An effective batch of 0.18 means on average you kept roughly 0.18 × 128 ≈ 23 prompts worth of signal per step; 0.06 is roughly 8. When it hits zero for many steps in a row, you are only paying for discarded rollouts.

These are not proxies I invented after the fact. They are the filter/batch fields the trainer already logs. The ranking they induce matches which jobs finished and which died.

What happened to A3

A3 scores answer fragments in tool responses as well as the final message. Offline, “call tools and say Done” scored almost as high as “call tools and report the answer” (perfect−empty advantage collapsed from 0.90 to ~0.01). Live, the same saturation showed up as:

  • Higher mean reward from step 0 (0.98 vs 0.90)
  • ~94% of groups filtered as zero-advantage (vs ~82% for A0)
  • Effective batch stuck near ~0.06
  • Ten consecutive steps where filters dropped all 128 rollouts
  • Job death: BackoffLimitExceeded

I am not claiming a fancy causal graph beyond the mechanism GRPO already implies: if within-group rewards do not differ, advantages vanish, filters empty the batch, training cannot proceed. A3 makes rewards look high while that contrast disappears. That is a reward-design failure that presents as “success” on the mean-reward chart.

What A1 taught us

A1 keeps final-message-only scoring but removes the elevated write-tool bonus. It finished 50 steps. It did not crash. Relative to A0 it still looked worse on health metrics: zero-advantage 89% vs 82%, effective batch 0.11 vs 0.18, and slightly lower average git_add / git_commit rates.

So the ranking is not only “works / dies.” A1 is the middle of a spectrum: still trainable, but less usable signal per dollar of rollouts. Offline, removing the write bonus wiped a 0.10 gap between “tried a write tool” and “only inspected” when the write outcome was still wrong. Live, we see the same direction on write-tool rates and filter health, not a second A3-style collapse.

Dashboard rules I would actually use

  1. Primary: effective batch size (fraction of nominal batch kept). Alert if it stays under ~0.1 for several consecutive steps; treat near-zero for 5–10 steps as an emergency.
  2. Primary: zero-advantage rate. Alert if it stays above ~0.9. That is “almost every group is a tie.”
  3. Secondary: mean reward. Useful for “is the task solvable at all,” bad as a solo health check. High mean + high zero-advantage is a red flag, not a win.
  4. Secondary: reward min across rollouts in a step. If the floor never drops (A3 often sat near ~0.6 while A0 could still hit 0.1), you may be over-crediting bad trajectories.
  5. Context: tool mix (write vs read calls). Checks whether the policy still attempts the hard actions you care about.

Why mean reward lies here

GRPO learns from within-group differences. A group where every rollout scores 0.98 is a great average and a useless gradient. Mean reward rises when the reward function is generous or when the policy improves. Effective batch falls when the reward function stops distinguishing good from bad.

In tool-use RL those two effects often move together: a buggy reward inflates scores and collapses variance at the same time. Offline ablations predicted that pattern; live A3 confirmed it by dying with a prettier mean than A0.

Limits

  • These are short 50-step runs, not full 300-step campaigns.
  • Effective batch and zero-advantage are platform filter metrics; exact filter thresholds are the trainer’s, not hand-tuned in this post.
  • A1’s effect is smaller than A3’s. I would not claim “write bonus alone saves training” from this data, only that A0 looked healthier than A1 on the signal metrics we care about.

Practical takeaway

If you are debugging agentic GRPO and the reward curve looks “too good,” open the filter panel before you celebrate. Rank runs by effective batch and zero-advantage first. The run that is about to die often has the prettiest mean.
