Effective Batch Is the Real KPI for GRPO Tool-Use Runs

Mean reward looked healthy on every ablation. Zero-advantage rate and effective batch size told you which run would die.

◆

If you only watch mean reward during agentic GRPO, you will miss the failure mode that actually ends runs.

We trained the same git tool-use environment three ways (short runs: 50 steps, batch 128, 8 rollouts). Mean reward was high for all of them. Only one finished in good health. One finished weak. One starved to death.

Zero-advantage rate is the fraction of groups where every rollout scores the same (or near enough that GRPO advantage collapses). High means the buffer has nothing useful to keep.

Effective batch size is what is left after filters. When it trends toward zero, you are not training: you are paying for rollouts that get discarded.

What happened to A3

A3 scores fragments in tool responses as well as the final message. Offline, that made “call tools and say Done” look almost as good as “call tools and report the answer.” Live, the same saturation showed up as:

  • Higher mean reward from step 0
  • Nearly every group filtered as zero-advantage
  • Ten consecutive batches where all 128 rollouts were dropped
  • Job death: BackoffLimitExceeded

That is not a flaky cluster. That is a reward function that looks successful while starving the optimizer.

What A1 taught us

A1 keeps final-message-only scoring but removes the elevated write-tool bonus. It finished 50 steps. It did not crash. It still looked worse on the health metrics than A0: higher zero-advantage, smaller effective batch, slightly less git_add / git_commit.

So the ranking is not binary “works / dies.” It is a spectrum of how much signal you leave on the table each step.

Dashboard rules I would actually use

  1. Primary: effective batch size (or 1 − filter rate). Alert if it stays near zero for N steps.
  2. Primary: zero-advantage rate. Alert if it climbs past ~0.9 and stays there.
  3. Secondary: mean reward. Useful for “is the task solvable,” bad as a solo health check.
  4. Secondary: reward min within groups. If min never drops (A3 floor ~0.6), you may be over-crediting bad rollouts.
  5. Context: tool mix (write vs read). Confirms whether the policy is exploring the hard actions you care about.

Why mean reward lies here

GRPO learns from within-group differences. A batch where every rollout scores 0.98 is a great average and a useless gradient. Mean reward rises when the reward function is generous or when the policy improves. Effective batch falls when the reward function stops distinguishing good from bad.

In tool-use RL, those two effects often move together: a buggy reward inflates scores and collapses variance at the same time. That is exactly the pattern offline ablations predicted and live A3 confirmed.

Practical takeaway

If you are debugging agentic GRPO and the reward curve looks “too good,” open the filter panel before you celebrate. The run that is about to die often has the prettiest mean.
